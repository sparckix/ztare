## Proposed algorithm (depth-traversal / file-prefix elaboration — critique this)

## Response

## Bottom line

Your proposal is conceptually right **only after three corrections**:

1. **Snapshot full `Command.State`/parser scope, not just an `Environment` id.**  
   `open`, `open scoped`, section `variable`s, local attributes, local notation, current namespace, private-name resolution, options, etc. are not faithfully recovered from environment alone.

2. **Use variant (b), but not by predeclaring `T := by sorry`.**  
   Open a proof session **inside the original declaration before the declaration is added to the environment**. If you first elaborate `theorem T ... := by sorry`, then `T` and its attributes may pollute the environment/simp set.

3. **Do not use full `import Mathlib` + forbid descendants.**  
   That prevents circularity, not historical leakage. Future independent lemmas are still unavailable at `T`’s declaration point.

Citations: Lean 4’s extensible/stateful elaboration model is described in de Moura–Ullrich, *The Lean 4 Theorem Prover and Programming Language*, CADE 2021, LNCS 12699, pp. 625–635. LeanDojo’s traced-source / accessible-premise design is the closest published benchmark precedent: Yang et al., *LeanDojo*, NeurIPS Datasets & Benchmarks 2023, arXiv:2306.15626, esp. Sec. 3 on tracing and premise availability.

## Correct leak boundary

For target occurrence `T` in module/file `F` at command offset `O`, the allowed declarations are exactly:

\[
A(F,O)=\{\text{decls in transitive imports of }F\}\cup\{\text{decls introduced earlier in }F\text{ before }O\}.
\]

Plus Lean kernel primitives / allowed imported axioms such as `Classical.choice`, `propext`, quotient axioms, etc. Exclude `sorryAx`.

A candidate proof is leak-tight only if:

- it is elaborated from the exact pre-command state `S(F,O)`;
- `T` is not yet in the environment while its body is elaborated;
- the candidate may fill only the proof hole, not add preceding commands;
- final proof-term constants are audited: no `sorryAx`, no constants outside `A(F,O)` except candidate-local aux constants whose own bodies pass the same audit.

`#print axioms` is insufficient because it reports axioms after unfolding theorem constants; it does not tell you that a proof term directly used `T` or a future theorem.

## Failure modes of the proposed algorithm

### 1. “Elaborate F’s own imports only”

Correct. If `lake env lean Mathlib/.../F.lean` succeeds, then `F`’s own imports suffice. Failures usually mean your runner is wrong: wrong module name, wrong Lake search path/options, missing generated files, platform/native-code issue, or source instrumentation changed messages.

Rare genuine breakage for Mathlib source. Treat as infrastructure bug unless the file is a test/example file with deliberate `#guard_msgs`, `#eval`, native code, etc.

### 2. “Declaration-by-declaration”

Wrong granularity. Lean files are processed **command-by-command**, not declaration-by-declaration.

Breaks or needs special treatment:

- `section`, `namespace`, `open`, `set_option`, `local notation`, `attribute [local ...]`;
- commands introducing multiple declarations;
- `mutual` blocks;
- `where` auxiliaries;
- equation/termination/generated declarations;
- command macros.

Use Lean’s parser/elaborator/info-tree, not regex.

### 3. `open`, `open scoped`, local/scoped notation

Common. Full prefix replay handles them. Regex scraping is not reliable.

Examples that fail outside the original command state:

```lean
open scoped BigOperators
theorem T : (∑ x in s, f x) = y := ...
```

or

```lean
local notation "μ" => MeasureTheory.volume
theorem T : μ Set.univ = ... := ...
```

The parser/name resolver needs the active scope state, not merely imported declarations.

### 4. `open ... in`

Handled only if you preserve the original command wrapper.

```lean
open scoped BigOperators in
theorem T : (∑ x in s, f x) = y := ...
```

If you extract only a bare signature, you lose the local open. Prefix replay plus in-place proof hole is fine.

### 5. `variable`, `include`, `omit`, auto-bound variables, universes

Variant (a) is fragile here.

Example:

```lean
universe u
variable {α : Type u} [Group α]

theorem T (a : α) : a * 1 = a := by simpa
```

A regex signature may not include `u`, `α`, `[Group α]`, binder implicitness, section variables, `include`/`omit` effects, or local instances. In-place source elaboration preserves all of this.

### 6. `private` / `protected`

- `private` prior lemmas are accessible inside the same file prefix but not from a later importing module. Prefix replay handles them.
- Full `import Mathlib` does **not** recover source-level access to same-file private aliases.
- Audit should reject direct use of imported private/internal mangled names unless they are same-file prefix private declarations.
- `protected` is mostly just name-resolution; original command state handles it.

### 7. Macros, `elab`, `deriving`, generated declarations

Prefix replay handles prior syntax/elaborator/tactic definitions because it actually runs the commands.

But targets that are themselves generated by:

- `deriving`;
- equation compiler;
- termination checker;
- `@[simps]`;
- `@[to_additive]`;
- command macros producing multiple declarations;

should be skipped unless you can identify a unique human proof hole. These are numerous among generated declarations but less problematic among ordinary source `theorem`/`lemma` commands.

### 8. `attribute ... in`, local attributes, target attributes

Prefix replay handles local attributes before the target, e.g.

```lean
attribute [local simp] foo
theorem T : ... := by simp
```

But do **not** pre-elaborate:

```lean
@[simp] theorem T : P := by sorry
```

and then search, because `T` may enter the simp set. Target attributes are applied after the declaration body is elaborated. For proof search, delay/strip post-declaration attributes unless the benchmark target is explicitly “prove the whole command including generated siblings”.

### 9. `mutual`, `where`, `termination_by`, `decreasing_by`

Previous such commands are fine if replayed normally.

Targets inside multi-declaration or recursive blocks are not clean single-theorem proof-search tasks. Skip by default. They are rare among human `theorem`/`lemma` tactic proofs, commoner among generated/definition artifacts.

### 10. `noncomputable`

Not a correctness issue if the original command state/modifiers are preserved. Regex/fresh reposing can drop it. For theorem proofs usually not decisive, but preserve it anyway.

### 11. Very large files

Not a soundness issue. Use per-file workers and checkpoint pre-command states. Clear messages/info-trees to avoid memory blowup. The prefix cost is amortized over all targets in the file.

## Is single-pass per-file snapshotting sound and cheap?

Sound **if and only if** the snapshot is the full Lean command state, not just the environment.

Lean command elaboration is a deterministic state transition:

\[
S_i \xrightarrow{\text{command } c_i} S_{i+1}.
\]

If you start from the same import environment and replay the exact source prefix under the same Lean/Lake options, the pre-target state `S_O` is the compiler’s original state at `T`. Then future same-file declarations and downstream modules are structurally absent.

Implementation requirements:

- use `lake env` / Lake search path and exact Lean/mathlib revision;
- process real source with Lean parser/elaborator, not regex snippets;
- snapshot `Command.State` including scopes/options/current namespace/private map/local attrs;
- restore checkpoint before every candidate attempt;
- never first add `T` via `sorry`;
- do not allow candidate text to contain top-level commands before the proof.

Cost:

- offline extraction: roughly one instrumented re-elaboration of Mathlib, parallelizable by module; expect around `1–3×` a source build depending on tracing/detail;
- online evaluation: group by file; load direct imports and replay prefix once; tactic calls then stay in the observed `~0.05–0.15s` regime except for expensive tactics;
- memory: persistent structures make checkpoints cheap, but clear message/info state.

LeanDojo-style traces are useful for source positions, tactic spans, and accessible-premise lists. They are not by themselves a live leak-tight environment unless paired with prefix replay / pre-command restoration. Pantograph or REPL frontends are acceptable only if they can enter a proof from the pre-command state; importing the completed module is not acceptable.

## Variant (a) vs (b)

### Variant (a): fresh name + regex signature

Do not build this.

Failure modes:

- drops section variables/universes/typeclass variables;
- loses `include`/`omit`;
- misparses notation/scopes;
- mishandles local/private names;
- changes namespace/name-sensitive generated aux names;
- cannot faithfully preserve command wrappers such as `open ... in`;
- loses declaration modifiers/attributes or applies them incorrectly;
- changes local hypothesis names, which breaks tactic scripts.

A Lean-generated explicit type with `pp.all` is less bad than regex, but still gives a different proof state and is unnecessary.

### Variant (b): original command + proof-hole

Canonical choice.

But the correct form is:

```lean
-- restore state before original command
theorem Original.Name ... : ... := by
  -- REPL-controlled proof hole here
```

while the declaration is still under construction. `Original.Name` is not yet in the environment, so self-reference is structurally impossible for ordinary nonrecursive theorem commands.

Do not do:

```lean
theorem Original.Name ... : ... := by sorry
-- now start proving from a state where Original.Name exists
```

That is contaminated.

## Full Mathlib + forbid target descendants is not leak-tight

Desired condition:

\[
\forall C\text{ used in proof},\quad C \in A(F,O).
\]

Descendant-DAG condition:

\[
\forall C\text{ used in proof},\quad T \notin \mathrm{Deps}(C).
\]

The second is strictly weaker.

Concrete counterexample schema:

```lean
-- F.lean
theorem T : P := p₁

-- later in the same file, independent of T
theorem U : P := p₂
```

For target `T`, declaration `U` is unavailable at `T`’s declaration point but is not a descendant of `T`. Under full `import Mathlib` plus “forbid descendants”, the proof

```lean
exact U
```

is accepted. This violates the benchmark’s stated precondition.

This is not rare in Mathlib in spirit: later stronger restatements, convenience lemmas, simp-normal forms, aliases, and downstream API lemmas often do not depend on the earlier target but can solve it.

Full-Mathlib + final dependency audit by **source position** can be useful for offline one-shot proof-term checking, but not for interactive tactic search: tactics, `simp`, typeclass search, `exact?`, premise retrieval, and environment-inspecting metaprograms have already seen future declarations. For your stated benchmark, reject this regime.

## The one algorithm to build

Build: **Lean-elaborator prefix replay with in-place proof-hole sessions.**

End-to-end:

1. **Build Mathlib at the pinned rev.**  
   Use exact Lean toolchain and Lake options.

2. **For each module `F`, spawn a clean worker.**  
   Load only `F`’s direct imports via Lake/Lean import machinery. Do not import `Mathlib` unless `F` itself does.

3. **Replay `F` command-by-command using Lean’s parser/elaborator.**  
   Before each candidate command, record a checkpoint of full `Command.State` plus source position.

4. **Identify candidates from syntax/info trees.**  
   Keep ordinary source `theorem`/`lemma` commands with tactic proofs. Skip generated declarations, multi-declaration commands, mutual blocks, theorem-command `where` auxiliaries, and commands whose proof hole cannot be uniquely localized.

5. **Pose the task by restoring the pre-command checkpoint and opening the original declaration body as a proof hole.**  
   Preserve section context, namespace, variables, notation, local attrs, options, private maps, etc. Do not register `T` by `sorry`.

6. **Gold validation.**  
   Re-elaborate the original command from the checkpoint. Require success and no `sorryAx`. Count tactic steps from the syntax/info tree. Count proof constants from the theorem value. Keep only tasks satisfying your operational multi-step filter, e.g.:
   - original proof has ≥3 real tactic nodes;
   - proof term uses ≥4 nontrivial allowed constants;
   - a fixed one-step solver suite fails from the initial state: `rfl`, `assumption`, `exact?`, `simp?`, `aesop?`, `omega`, `ring_nf`, `linarith`, `norm_num`, `decide`, etc.

   Absence of all possible one-line proofs is undecidable/too expensive; define this operationally.

7. **Candidate validation.**  
   Candidate systems may fill only the proof hole. Restore the checkpoint for every attempt. After success, collect direct constants in the produced proof term and reject if any are outside the pre-command allowed set, are target/current-command declarations, are imported private/internal names not source-accessible, or include `sorryAx`.

8. **Premise/retrieval corpus.**  
   For each task, expose only imported declarations plus same-file prefix declarations. Do not expose target proof, target declaration as premise, later same-file declarations, or downstream modules.

Expected yield: for your already multi-step source theorem candidates, expect the gold-compile keep rate to jump from `0.13%/1.5%` to roughly `>85–90%`, with losses mostly from generated/multi-declaration/weird-attribute commands and timeouts. Across all named Mathlib theorem constants, after restricting to source tactic proofs and multi-step tasks, expect roughly `20–40%` usable.

VERDICT: partially — the direct-imports/file-prefix idea is right, but build the full-command-state in-place proof-hole algorithm, not regex fresh names and not full-Mathlib descendant filtering.
