## Pressure test of your seven suspected candidates

### 1. Proof-state feedback

**Yes, highest-value.** Without live goals, you cannot do credit assignment. A proof of depth `d` generated whole-cloth succeeds only if every local choice is right. If per-step validity is `p`, whole-proof success behaves like roughly `p^d`. Stepwise search can discard bad prefixes and resample only the failing branch.

Mature systems expose proof states for this reason: LeanDojo/ReProver uses Lean interaction and retrieval-augmented state-conditioned proving; Aesop is explicitly best-first search over proof states/rules; COPRA-style agents use proof-state feedback/backtracking; Graph2Tac/TacticToe-style systems learn state/action policies.

Relevant citations: LeanDojo/ReProver, arXiv:2306.15626. Aesop: Limperg/From, “Aesop: White-Box Best-First Proof Search for Lean,” CPP 2023. TacticToe: Gauthier et al., arXiv:1804.00596. COPRA: arXiv:2310.04353.

### 2. Tactic-by-tactic stepping vs whole-proof compile once

**Whole-proof compile once is the wrong default.** It is acceptable only as final verification or for very short proofs.

You need:

```text
state s_i
  -> propose tactics a_1 ... a_k
  -> Lean elaborates each
  -> accepted actions yield successor states s_{i+1}
  -> score/hash/cache/backtrack
  -> final theorem checked by kernel + #print axioms
```

Do not merely ask the LLM for a complete `by ...` block and then verify.

### 3. Goal-conditioned premise retrieval

**Statement-conditioned retrieval is a weak proxy.**

Example pattern:

```lean
theorem T : ∀ x, P x → Q x ∧ R x := by
  intro x hx
  constructor
  · -- goal Q x, local hx : P x
  · -- goal R x, local hx : P x
```

The original statement retrieval sees `∀ x, P x → Q x ∧ R x`.  
The live subgoal retrieval sees `x`, `hx : P x`, target `Q x`.  
Those are materially different premise-selection problems.

Cheapest experiment: compare used-premise rank before and after `intro`/`constructor` on existing mathlib proofs.

### 4. In-REPL search oracles

**You should reverse the earlier minimization.** The previous cost model was false.

Use oracles as proposal generators, not as trusted solvers. Final proof still goes through Lean and your axiom whitelist.

Priority order:

1. Cheap closers: `rfl`, `assumption`, `contradiction`, `simp`, `simp_all`, `norm_num`.
2. Searchy Lean tactics: `aesop?`, `exact?`, `apply?`, `rw?`, `solve_by_elim`.
3. Domain tactics: `omega`, `linarith`, `nlinarith`, `ring_nf`, `field_simp`, `positivity`, `gcongr`.
4. Structural tactics: `intro`, `constructor`, `cases`, `rcases`, `ext`, `induction`.

### 5. Stronger ATP backends

**Worth adding, but not the top cap.** Duper/lean-auto/hammers help most when the subgoal is first-order/equational and the right premises are selected.

Do not expect them to solve dependent-type-heavy proofs, sophisticated induction, or high-level analysis alone.

Correct integration:

```text
live goal
  -> retrieve accessible premises
  -> ATP/Duper/lean-auto attempt
  -> reconstruct Lean proof
  -> #print axioms gate
```

### 6. Benchmark/corpus extraction with dependency-DAG context

**Critical.** If you evaluate with `import Mathlib`, you may allow:

```lean
exact target_theorem
```

or use later theorems unavailable at the original declaration point. `#print axioms` will not detect that as cheating.

You need original module context, declaration order, imports, namespaces, scoped notation, local instances, and dependency labels. This is one of LeanDojo’s main structural lessons.

### 7. Multi-process parallelism

**Immediate wall-clock win now that import is amortized.**

But do it as a warm worker pool, not per-probe Lean invocations:

```text
N persistent REPL workers
each imports once
controller assigns independent states/goals
workers return accepted successors/suggestions
global ledger deduplicates by state hash
```

On an 8-core machine, expect memory to cap you before CPU. Try 4 workers first, then 6/8.

## Cheapest decisive experiment for the top missing piece

Implement a minimal **stateful REPL beam prover**.

Dataset:

- 150–300 current unsolved but believed-true goals.
- Same Mathlib/Lean pin.
- Same axiom gate.
- Fixed wall-clock budget per theorem, e.g. 10–30s.

Baseline:

- Your current whole-proof compose-then-compile pipeline.

Treatment:

- Start from theorem goal.
- Maintain beam of proof states.
- At each state, propose one-tactic actions from:
  - oracle portfolio: `exact?`, `apply?`, `rw?`, `aesop?`, `simp_all`, `omega`, `linarith`, `ring_nf`, `norm_num`;
  - structural actions: `intro`, `constructor`, `cases`, `ext`;
  - existing agent, but prompted only with current goal/local context.
- Execute one tactic through REPL.
- Keep only elaborated successor states.
- Hash normalized goals to avoid duplicates.
- Final closure checked with `#print axioms`.

Decision rule:

- If treatment gives **≥2× closures** or many new partial reductions, proof-state search is the missing cap.
- If treatment gives **<1.2×** and no meaningful partial progress, then your bottleneck is likely premise retrieval/model quality/domain automation instead.

My prior: this experiment will be positive.
