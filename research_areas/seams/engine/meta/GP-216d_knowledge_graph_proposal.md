# GP-216d — Knowledge-Graph Representation for ZTARE Artifacts

**Status:** active *(inferred 2026-05-08 — needs operator review)*

*2026-05-05. Proposal note in response to operator question: would a graph-database representation compress ZTARE knowledge better than the current text-based seams + arch maps for LLM consumption? Position-paper, not implementation. Concrete schema + small prototype + cost-leverage recommendation.*

## Why this matters

ZTARE produces a lot of text artifacts — seams (~170), F-rows (~600), gates, mandates, papers, advisor turns, evidence files. Each is semi-structured markdown + JSON. LLMs read these as flat text; the relationships between artifacts (depends_on, instantiates, falsifies, supersedes, cites) are encoded in prose ("see GP-148 for context"; "this seam shipped GP-149 §2.2 plateau guard") rather than in structure.

**The problem this creates:** when an LLM (Director, judge, or operator-launched) needs context for a specific question, it has to read many text artifacts and re-parse implicit relationships from prose. The compression seam (GP-167) + architecture maps (GP-148/167) help, but they're themselves text.

A graph database (or property-graph format like JSON-LD) would make relationships first-class. An LLM querying "what's the failure-history of NS Track B's bound-chain pricing approach?" would traverse edges instead of re-reading 30 advisor turns.

## What's already in place

ZTARE has implicit graph structure:
- Seams reference other seams ("Per GP-149 ...")
- F-rows reference seams + projects
- Gates reference rubric metadata
- Mandates reference seams + gates
- Papers cite F-rows + seams + each other

Recent compression efforts (GP-148 mining infrastructure, GP-167 architectural maps) already extract structured signals (delta_type, structural_move_class, what_survived, depends_on chains). These are graph-shaped data hidden inside text artifacts.

## Proposed schema (property-graph)

### Node types

| Type | Examples | Key properties |
|---|---|---|
| `seam` | GP-216, GP-148 | id, status (open/closed), date, charter_summary, current_pass |
| `f_row` | E-GP216-PASS11-…, F-NS-TRACKB-… | id, date, finding_summary, severity, scope |
| `gate` | PotentialFunctionMonotonicityGate | id, mechanizes_op, fail_closed (bool), substrates_deployed |
| `op` | core_01, broad_03, spec_01_graph | id, name, tier, structural_mechanism, n_subfields |
| `paper` | paper5, paper5b | id, title, status (draft/published), claim_level (A/B) |
| `mandate_addendum` | v1.19, v1.20 | id, version, date, scope_summary |
| `substrate` | NS Track B, GP-156 sandbox | id, status, current_phase, op_fingerprint |
| `theorem` | no_X_falsifier_with_Y_receipt | id, lean_path, proves, falsifies |
| `gap_type` | thesis_fits_in_distribution_only | id, canonical_name, suggested_op_class |

### Edge types

| Edge | Source → Target | Semantics |
|---|---|---|
| `depends_on` | seam → seam | conceptual dependency |
| `instantiates` | f_row → seam | f_row reports on seam's pass |
| `mechanizes` | gate → op | gate is runtime check for op |
| `aliases` | op (v3) → op (v4) | legacy → current op-id mapping |
| `falsifies` | theorem → claim | theorem refutes claim |
| `supersedes` | mandate_addendum → mandate_addendum | newer overrides older |
| `cites` | paper → seam, paper → f_row | external citation |
| `op_fingerprint` | substrate → op (with weight) | substrate's structural-mechanism distribution |
| `gap_to_op` | gap_type → op | suggested op-class for repairing gap |

### Format

JSON-LD (subset of RDF), or property-graph format (Neo4j-style). For LLM consumption, JSON-LD is more tractable (JSON-native; easy to embed in prompts).

Keep two graph layers distinct:

1. **Seam/navigation graph** (`@context: ztare://kg/seam/v1`). Nodes are seams, F-rows, gates, papers, mandates, substrates, and op-classes. Edges come from YAML frontmatter plus explicitly marked cross-references; regex-only GP-XXX mentions are allowed only as low-confidence bootstrap edges.
2. **Lean/content graph** (`@context: ztare://ns-trackb-proof-graph/v1`). Nodes are Lean files and declarations. Edges come from imports and declaration-use references. This graph is a proof-spine index, not a prose-navigation index.

They may be generated by adjacent scripts, but they should remain separate JSON-LD files or separate top-level namespaces. Mixing them makes the seam graph look more semantically grounded than it is, and makes the Lean graph inherit prose false positives.

## Why this might compress better for LLM use

1. **Relationships are first-class.** An LLM querying "what gates mechanize core_02?" gets a deterministic answer (one query) instead of grep + parse + cross-reference 30 markdown files.

2. **Path queries replace text-search.** "Find all F-rows that report on a seam that mechanizes op X" is a 3-hop graph query; the equivalent text-based search requires reading every F-row and parsing the seam reference.

3. **Navigation cost reduction: the text artifacts can stay; the graph is the index.** The full markdown remains for human review; the graph is a structured index over it. LLMs reading via the graph load the graph index first, then load only the source artifacts touched by the query.

4. **Discoverable absences.** "Which seams have no closing F-row?" is one query. In text, this requires manual audit.

## Why it might NOT be worth it

1. **Maintenance cost.** Every new seam + F-row + gate would need a graph entry. If the graph isn't authored alongside text, it rots.

2. **LLMs handle text well.** Modern LLMs have 200K-1M context windows. They CAN read all 170 seams in a single pass if needed. The compression-via-graph saves tokens but might not be decisive if context-window growth keeps up.

3. **Implicit relationships matter.** Graphs make explicit edges; some decisive relationships in seams are still prose ("the second-order critique here is..." — graph edges can't capture nuance).

## Cost-leverage recommendation

**Don't build a full graph DB. Build a thin layer that auto-generates JSON-LD from existing markdown frontmatter + cross-references.**

Specifically:
1. **Phase 1 (1-2 days):** Establish separate JSON-LD contexts/files for the seam graph and the Lean proof graph, and add YAML frontmatter to new/critical seams declaring `id`, `status`, `depends_on`, `instantiates_op`, and edge confidence. Existing GP-XXX regex extraction remains a bootstrap, but edges inferred only from prose mentions must be marked `confidence: inferred`.
2. **Phase 2 (1-2 days):** Script that walks `research_areas/private/seams/`, extracts frontmatter + cross-references, emits `analytics/public/queries/graphs/ztare_knowledge_graph.json` (JSON-LD).
3. **Phase 3 (1 day):** LLM helper `query_knowledge_graph(question_text)` that traverses the graph and returns relevant nodes' content. This is the decisive tool — Director-level use.

Don't move to Neo4j or any actual graph DB. JSON-LD on disk is sufficient and zero-infrastructure.

**Test for whether it's worth it:** measure how often Director / judge / operator-launched LLM needs context that requires reading >5 text artifacts. If frequent → graph helps. If rare → don't bother.

**My intuition:** Director-level synthesis (advisor channel turns synthesizing across substrates) is the highest-leverage use case. Currently a synthesis turn requires loading ~10-30 artifacts. A graph-query reduces that to ~3-5 most-relevant nodes + their immediate neighborhood.

## What this is NOT

- Not a replacement for seams or F-rows. Those stay as the canonical human-readable records.
- Not a control-flow change. The graph is a READ-ONLY INDEX.
- Not part of mandate v1.20 standing duties. Director may USE the graph; not REQUIRED to maintain it (initial maintenance is operator + Codex-assisted).

## Decision point — REVISED after running the prototype

I initially recommended deferring this until ~500 seams scale. **That was wrong.** Running the actual extractor over 137 seams produced the following metrics:

- 459 edges across 137 nodes
- Average out-degree: 3.4 (cross-reference density is real)
- Graph density: 0.0246 (above 0.01 "sparse" threshold)
- **Index size: JSON-LD index is 2.8% of full seam text** (440K tokens → 12K tokens). This is not the full operational token saving: a real Director query still loads the graph index plus the 3-5 source seams it touches. Realistic consumption is closer to 25K-60K tokens than 12K. The win is not "97% compression"; it is moving from "read everything" to "read the relevant neighborhood."

The structure is already dense enough today. Top depended-on hubs (GP-023, GP-088, GP-035, GP-072) demonstrate decisive cross-references that any Director synthesis turn already navigates implicitly.

**Revised recommendation: ship the graph layer now, not in v1.21.** Concrete plan:

1. Prototype already shipped at `analytics/public/queries/graphs/ztare_knowledge_graph_prototype.json` (12K tokens of JSON-LD covering 137 seams + 459 edges)
2. Phase 2 (~30 min): `make seam-graph` target for regeneration on demand
3. Phase 3 (~1 hour): `src/ztare/knowledge_graph/query.py` Director-query helper (`query_graph("what depends on GP-216?") → traversal result`)
4. Phase 4 (~2 hours): harden frontmatter coverage for high-degree seams and all newly opened seams so `depends_on` is not inferred from passing prose mentions alone.

Total to v1 utility: ~2.5 hours autonomous operator-light work. The prototype proves density; the next decisive hardening is frontmatter on high-degree seams so `depends_on` edges are not grep-shaped false positives.

**What changed my mind:** running the extractor produced empirical density numbers I could not have predicted from intuition. 3.4× average out-degree is non-trivial, and the index makes relationship discovery cheap enough to field-test. Future-direction work should run prototypes like this BEFORE writing recommendation prose; otherwise the recommendation is only a story about expected leverage. Lesson logged as a general rule.

## 2026-05-05 23:32:00 — NS Track B content-graph field test

The GP-216d graph pattern was applied directly to the NS Track B Lean proof
surface as a content-layer proof-spine index, not just a navigation graph.
Implementation artifacts:

- `scripts/public/projects/ns/ns_trackb_graph.py` extracts a JSON-LD graph from
  `ztare_proofs/ZtareProofs/ns_*.lean` into
  `projects/ns_millennium_hunt/workspace/queries/ns_trackb_artifact_graph.json`.
- `scripts/public/projects/ns/ns_trackb_closure_miner.py` consumes that graph, derives a
  provisional GP-219 A/C/D closure rubric, runs the auxiliary-object,
  limit-passage, and threshold-dichotomy gates, and ranks proof targets.
- `scripts/public/projects/ns/ns_gate_check.py` now wraps all three GP-219 estimate-craft gates
  (proto-A auxiliary object, proto-C threshold dichotomy, proto-D limit
  passage) in addition to the original GP-216 gates.

Empirical graph snapshot after the field test:

- 1,610 nodes: 156 Lean files + 1,454 declarations.
- 4,134 declaration-use edges.
- 0 detected dependency cycles.
- Top decisive declarations:
  `FullLedgerBlock`, `FullLedgerNoSurvivor`, `cycleGain`,
  `ThresholdDefectConvexity`, `LowHighKinematicDichotomyLedger`,
  `ContinuumLPPrefixPriceStream`, `LowFrequencyLipschitzLedger`.

The graph produced two nontrivial proof-spine changes:

1. It exposed that the flat-torus/Killing symmetry-breaker was not
   decisive in `GP216BridgeCompositionReceipt`.  The receipt was patched so
   `FlatTorusKillingModeConclusion` and
   `FlatTorusLowHighKinematicPDEObligation` now feed the phase-latency capacity
   branch.
2. It exposed that `EventRecurrencePricePDEObligation` was a floating
   obligation with zero reverse uses.  The event PDE duty list was converted
   into `EventRecurrencePricePDEObligationSatisfied`, and
   `GP216BridgeCompositionReceipt` now requires it before excluding harmonic
   recurrence escape.

Interpretation: the graph is complementary to ZTARE.  ZTARE remains the
creative/adversarial proposal engine; the graph is the proof-spine accountant
and, after field validation, a possible hint surface for future mutator prompts.
Recommended integration is a pre/post wrapper, not immediate core-loop
entanglement:

- **Pre-run:** use `ns_trackb_closure_miner.py` to generate the closure-target
  rubric and evidence prompt from actual Lean dependencies.
- **Post-run:** map submissions back onto graph obligations to detect
  false-positive closures, disconnected receipt islands, and false negatives
  hidden in submissions.
- **Promotion criterion:** after 3-5 NS closure attempts, keep only the graph
  checks that catch real proof-spine gaps or prevent real ZTARE scoring errors.
- **Possible next experiment:** after those 3-5 closure attempts, feed ranked
  gap nodes from the proof graph into ZTARE as advisory targets. This must be a
  hint surface, not a hidden answer key or gate-shaped tautology.

This validates the content-layer hypothesis in a narrow sense: graph algorithms
did not prove new PDE estimates, but graph queries generated concrete Lean
lemma obligations and removed two non-decisive closure illusions.
