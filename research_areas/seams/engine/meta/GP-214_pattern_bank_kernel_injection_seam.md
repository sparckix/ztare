## Eigenquestion

> The kernel already injects abstract failure modes via the anti-pattern catalog (I-1). Should it also inject *exemplar-grounded* failure modes from the mining-derived pattern bank, and if so, under what dispatch policy?

## What the pattern bank is

A mining-derived corpus, refreshable on each mining run, that groups debate-log critiques by class label and emits one structured markdown entry per class (≥ N=10 records). Each entry contains:

- Class name + mining N count + project-count
- Mechanism description (one paragraph)
- 3–5 redacted exemplar critiques pulled from real ZTARE runs
- A generic "killer question" the mutator should answer to clear the class

Today the bank is generated by `scripts/public/mining/build_mini_ztare_pattern_bank.ts` and published to two destinations:
- Operator-private: `analytics/public/queries/pattern_bank_redacted/*.md` (15 files, May 4 generation)
- Mini-ZTARE: `mini-ztare/corpus/pattern_bank/*.md` (gitignored; embedded into `corpus/embeddings.json` for retrieval)

## Why this is structurally distinct from I-1 (anti-pattern catalog)

| Layer | I-1 anti-pattern catalog | I-5 pattern bank |
|---|---|---|
| Source | Operator-curated, hand-written | Auto-generated from LLM classifier on debate logs |
| Granularity | 9 abstract families | 15 classes with mining N counts |
| Content | Pattern + mechanism + boardroom translation | Pattern + mechanism + 3–5 *real* exemplar critiques + N |
| Grounding | Vocabulary | Evidence |
| Refresh cadence | Manual | Auto (re-mine → re-generate → re-embed) |
| Use today | `inject_antipattern_catalog: hardkill/ceilingbreaker/both` | None |

The two are *complementary*. I-1 gives the mutator vocabulary it can map onto its claims; I-5 gives the mutator concrete past-failure exemplars in its substrate's class. A mutator armed with both has both abstract guards and concrete priors.

## Three candidate dispatch modes

The intervention's leverage depends on dispatch. Cross-LLM audit (GP-149 §10) constrains which modes are safe today.

**Mode A — Manual (green, ship now).** Operator sets `inject_pattern_bank_class: <class_name>` in the rubric. Autoresearch loop reads the flag and appends the matching bank entry's exemplars + killer-question to the mutator's grounding payload, alongside the abstract catalog if I-1 is also on. Operator chooses the class manually based on substrate type and prior runs.

**Mode B — Single-class auto-route (amber, experiment first).** Limit auto-routing to one class: `catastrophic_fit_failure` (cross-LLM stability 0.538, the highest in the May 4 audit). When the runtime classifier (regex layer at `src/ztare/validator/weakest_link_classifier.py`) detects this class on a recent iteration, kernel auto-injects the bank entry on the next iteration. Experiment: A/B with and without the auto-injection; if it moves the apparent failure rate, mode B graduates. If not, mode B is buried.

**Mode C — Multi-class auto-route by predicted substrate class (red, blocked).** The original I-5 ambition: kernel uses the LLM classifier to predict the class on every iteration, looks up the bank, injects the matching entry. **Blocked** by the GP-149 §10 cross-LLM stability finding (42 % three-way, < 0.60 threshold). Defer until the classifier passes; may require a different classifier architecture.

## Manual mode spec sketch

**Rubric flag.**
```yaml
inject_pattern_bank:
  enabled: true
  source: "analytics/public/queries/pattern_bank_redacted/"
  class: "catastrophic_fit_failure"  # operator-supplied class label
  exemplar_count: 3                  # how many exemplars to surface (cap 5)
  position: "after_antipattern_catalog"  # before|after|replace I-1
```

**Autoresearch loop hook.** Add to the grounding-payload assembly step:

```python
if rubric.get("inject_pattern_bank", {}).get("enabled"):
    cls = rubric["inject_pattern_bank"]["class"]
    bank_path = Path(rubric["inject_pattern_bank"]["source"]) / f"{cls}.md"
    if bank_path.exists():
        grounding_payload["pattern_bank_entry"] = bank_path.read_text()
    else:
        log.warning(f"pattern_bank class {cls} not found; skipping injection")
```

**Operator-override log.** When the flag is set, write an entry to `analytics/public/operator_overrides.jsonl`:

```json
{"timestamp": "...", "project_id": "...", "iteration": N, "intervention": "I-5_pattern_bank", "class": "catastrophic_fit_failure", "source": "manual"}
```

This becomes the dataset for evaluating I-5's effectiveness later (compare apparent-failure rate on iterations with vs. without the injection, controlling for substrate class).

**Validation gates.**
1. Pattern-bank entry must be < 4 KB (it is one redacted markdown file; this should be trivially true).
2. Exemplars must already be redacted (regex check for project IDs, operator names, charter hashes). The generation script enforces this; the runtime check is a defense in depth.
3. Class label must exist in the bank directory; missing = warning + skip, not error.

## Auto mode (Mode B) experiment design

**Goal.** Determine whether auto-injecting `catastrophic_fit_failure` exemplars on the next iteration after the runtime classifier detects this class moves the apparent failure rate of that class.

**Setup.**
- Pick 20 substrates that historically show ≥ 1 iteration with `catastrophic_fit_failure` (read from `analytics/public/ledgers/trajectory/trajectory_archive_enriched.jsonl`).
- Random A/B: 10 with mode B on, 10 with it off.
- Run each for 30 iterations.
- Measure: % of iterations after the first detection where `catastrophic_fit_failure` re-fires on the runtime classifier.

**Pass criteria.** Mode B reduces re-fire rate by ≥ 25 % relative, with p < 0.05 on a paired test. Otherwise mode B is buried.

**Cost.** ~600 iterations across 20 substrates. Half a day of compute on a single mutator instance.

**Reality check (2026-05-04 post-build).** The harness shipped today
(`scripts/public/audits/run_i5_mode_b_experiment.py`) ran against the trajectory
archive with the just-extended runtime classifier and found only **2** projects
with `catastrophic_fit_failure` hits (`mlh_f5`: 3 hits in 19 iters;
`gp069_sandbox_13`: 1 hit in 31 iters). The 20×30 design is therefore
under-powered at the current data scale. Two responses are reasonable:

1. Run the underpowered experiment as a directional probe rather than a
   gated test; treat the result as evidence rather than verdict.
2. Run on a per-iteration basis instead of per-project: reload the matched
   iterations, replay both arms (with and without injection) on each, and
   compare apparent re-fire on the very next mutation. This is a stronger
   per-event test but requires replay infrastructure not in v0.

Recommendation: ship the underpowered probe (response 1) and decide whether
the per-iteration replay is worth building based on the directional result.

The harness output is at
`analytics/public/queries/i5_mode_b_experiment_plan_<TIMESTAMP>.md` (control + treatment
CLI commands ready to run).

## Mode C un-blocking conditions

Mode C requires the LLM classifier to pass GP-151's PATH_C_ONLY threshold of three-way agreement ≥ 0.75 (super-class) or ≥ 0.60 (class-level). Today: 0.42 three-way. To un-block:

1. Try a stricter classifier prompt (force one-class output, deny multi-label, force cite-evidence-span format). May lift agreement.
2. Try a smaller class set (collapse the 15 classes into ~6 super-classes per `docs/concepts/problem_class_taxonomy.md`). Larger super-class buckets typically lift agreement.
3. Try a single-classifier source-of-truth (drop cross-LLM, use a fine-tuned classifier whose accuracy is calibrated against operator labels). Different gate, but defensible.

These are tracked as candidate follow-ups; no commitment to any without operator review.
