# Evidence-context finite-family capability pencil

Date: 2026-07-19

## Eigenquestion

Can a campaign-authored, finite, data-only construction family cross an
evidence-incidence language boundary without either importing generated code
or letting the host choose the family mathematics?

## Governing identity

The object is a campaign-local reviewed family application. Its job is to
bind an ordered finite parameter domain to inert witness artifacts and to
join every member to the active adapter's existing normalizer and verifier.
The campaign leaf owns the family bytes and parameterization; AdapterForge's
independent reviewer owns admission; the common host owns identity, coverage,
deterministic replay, and outcome aggregation; the substrate adapter owns
normalization and predicate semantics. The family never enters the global
adapter registry.

An evidence-incidence context and a formal-theory context are distinct
context categories with one shared boundary requirement: a byte-frozen
snapshot whose `context_hash` matches the language request. Workspace staging
must preserve that category instead of requiring the formal-theory subtype.

## Falsifiable claim

A third AdapterForge interface,
`leanmill.reviewed_finite_construction_family.v1`, is sufficient to make the
current length-51-to-50 request executable while remaining substrate-neutral.
The interface is an explicit ordered relation

\[
  p \in P \longmapsto A_p,
\]

where `P` is finite and byte-frozen and each `A_p` satisfies the active
witness schema. No generated lowering code is imported. After independent
review, the host invokes the registered adapter normalizer and verifier twice
per distinct artifact and emits a coverage-preserving member join.

## Candidate transition

1. Stage exactly one frozen context snapshot under its declared category.
2. Resolve only campaign-declared evidence files referenced by context object
   records; copy them read-only into the quarantine and verify every selected
   JSON fragment against its declared content digest.
3. Let AdapterForge author an explicit family artifact before any target
   member is evaluated.
4. Validate family/request/context/adapter identity, exact declared-versus-
   observed parameter IDs, artifact schema, content digests, and no registry
   mutation.
5. Obtain an independent review bound to the host validation receipt.
6. Only then execute the existing registered normalizer and verifier and
   aggregate `witness_found`, `exhausted`, or `unavailable`.
7. Return an exhausted or unavailable result as typed evidence to navigation;
   retain any accepted member as `discovered_pending_ratification`.

## Claim boundary

`exhausted` speaks only about the exact reviewed family digest. It does not
imply nonexistence in the ambient substrate. Exact host verification is not
kernel ratification. A positive member is not a priority or novelty result.

## Kill conditions

- A missing, extra, duplicated, or reordered parameter can still aggregate as
  exhausted.
- Family bytes can change after review without invalidating execution.
- Any member can be credited without a deterministic registered-adapter
  verifier receipt.
- An unavailable member is counted as a rejection.
- Evidence files outside the campaign manifest can be staged, or a JSON
  fragment fails its declared digest without stopping.
- The host selects or synthesizes family members.
- The live adapter registry changes.
- The change requires binary-code vocabulary in the common family module.

## Intended checks

The first stress suite will cover evidence-context staging, missing/extra
members, duplicate artifact multiplicity, mutation after review,
nondeterministic capability replay, unavailable-member aggregation, positive
status separation, and formal-context regression. The live discriminating
test is resumption of the signed successor attempt from its preserved adapter
gap; success means the campaign itself authors and reviews the family and the
host returns a complete typed execution receipt.
