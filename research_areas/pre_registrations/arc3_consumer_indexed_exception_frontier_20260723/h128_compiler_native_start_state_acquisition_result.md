# H128 result — automatic recall controlled the fork, then decayed

Status: **compiler consumption supported; task criterion failed**.

Three fresh Sol-max treatment controllers received the exact H127 compiler
digest at the full Level-2 start. Three matched controls received a mechanical
redaction with the same action map, observed bearing, common approach, route
distances, budget, uncertainty, scope, retrieval cost, and 3,912-byte prompt
length, while the learned relation and branch selection were removed.

Treatment followed the registered seam `[0,3,3,1]` in `3/3` arms. Control did
so in `0/3`; the +3 difference passes the primary compiler-consumption
criterion. Treatment completed the level in `1/3` arms and control in `0/3`,
so the fixed task threshold did not pass.

The successful arm executed the exact ten-action oracle path. The other two
treatments retained the learned approach and branch but diverged later: one
inserted an extra right before contact, and one inserted an extra up after
contact. This is evidence against treating one-shot recall as a persistent
policy. The compiled judgment remained useful across four delayed actions,
then lacked a mechanism to re-bind its authority to the state created by those
actions.

The independent audit passed 16 global checks over six unique sessions and 60
successful exchanges. It independently reconstructed the compiler digest,
verified the fresh context and preserved memory identity, checked all 15
redaction leaves, and deterministically replayed every observation.

The next discriminating test is recurrent state-conditioned re-evaluation:
hold the source memory and initial recall constant, then compare a digest
recompiled from each current observation with an equal-cost stale-memory
refresh. This tests whether event-sensitive working memory converts the
acquisition effect into task completion.
