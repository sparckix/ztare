# Cross-epoch success-neighborhood transport hypothesis

Date: 2026-07-26

Hypothesis ID: `H-ARC3-CROSS-EPOCH-SUCCESS-NEIGHBORHOOD-20260726-25`

## Eigenquestion

Can a prior successful action edge be transported across level ontologies from
the rooted operation/effect structure around its source, without comparing
rendered coordinates?

## Hypothesis

The two authoritative success sources share a finite rooted transition
neighborhood after permitted symmetries: operation-label renaming and
mechanism-effect family normalization. A depth-at-most-three canonical
neighborhood code learned from epoch 0 will recover the epoch-1 success source
more selectively than the coarse set of lifecycle-boundary sources. Its
reciprocal code will do the same from epoch 1 to epoch 0. Applying the surviving
code to the active graph will nominate at least one source outside the known
non-discharge boundary sources.

## Governing identity

The tested object is an advisory `success-edge transport candidate`: source
success edge, target rooted graph neighborhood, explicit symmetry, and
evidence lineage. It neither mutates `AuthoritativeGoalEdgePredicate` nor
becomes a goal predicate. Equality is canonical rooted-neighborhood equality
under the declared symmetry.

## Discriminating test

Compile one partial-action graph per source epoch from sealed evidence. Coarsen
all lifecycle boundaries equally so the positive label cannot leak into the
fingerprint. Compute exact rooted refinement codes at depths 1–3 for four fixed
symmetry families:

1. operation-preserving, exact mechanism effects;
2. operation-renaming, exact mechanism effects;
3. operation-preserving, normalized mechanism-effect families;
4. operation-renaming, normalized mechanism-effect families.

Hold out epoch 1's success label while matching the epoch-0 success source, then
reverse the direction. Compare each match set with the boundary-source
baseline. Apply only a bidirectionally surviving code to the active graph and
measure overlap with known non-discharge sources.

## Success criterion

At least one fixed code contains the held-out success source in both directions,
is no broader than the lifecycle-boundary baseline in either direction and
strictly narrower in at least one, and yields an active candidate outside the
known non-discharge boundary sources.

## Kill condition

No exact cross-epoch match; match sets are only the lifecycle-boundary class;
the reciprocal check fails; all active matches are already known
non-discharge sources; or the result requires a rendered coordinate, success
label, learned weight, or action-name assumption.

## Claim boundary

Passing produces candidate transport lineage only. A live external task event
is still required for completion.
